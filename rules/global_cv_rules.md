# Global CV & Cover Letter Rules

Rules for the resume and cover letter drafting loop (`/apply`). They apply to every CV and cover letter, regardless of company or role. A user's own rules in `state/cv/rules.md` override these. Keep this file free of personal facts. Rule numbers are stable, so rules are numbered in the order they were added, not always in sequence.

## Bio

1. **Role-specific framing, not a fixed formula.** Lead the bio with whatever is most relevant to *this* role (e.g. healthcare + trust for a healthcare AI company, platform ownership for a platform role). Don't default to a generic opening. Target **~200–250 characters** total.
2. **Name before you describe.** When a clause names something concrete with supporting specifics attached, name the noun first, then unpack the specifics after a colon, not the reverse. (e.g. "...on a $2B payments platform: fraud checks, multi-currency settlement, chargebacks", not the specifics piled up before the noun.)

25. **Implied first person, tense matched to whether the work is finished.**
   - **Perspective:** no pronouns: no "I"/"my", and no third-person name. Explicit first person belongs in cover letters and LinkedIn About, not the CV bio.
   - **Shape:** sentence 1 is an identity phrase with no tense (title + background + specialty). Sentence 2 is verb-led proof: the key problem(s) solved, at scale, that relate to *this* job. One is the default; two is fine when both are relevant; three is a stretch but acceptable if it stays within the character target and is compelling for the role.
   - **Tense:** finished work is past tense ("Launched", "Took", "who built"). No present participles ("building", "driving", "taking") for finished work. Present tense only for what is still true: an ongoing identity ("hands-on AI builder"), a live personal project, or a platform's current scale ("now behind $2B").
   - **Title:** lead with the user's strongest accurate title. "Product leader" is acceptable for a senior IC, but never imply people management (see rule 7).
   - **Length:** stays within rule 1's ~200–250 characters (roughly 30–50 words).

## Work history

3. **Don't undersell short tenures with duration framing.** Never open a role's story with "I spent a year/X months at...". State the skill, method, or result directly instead.
4. **Bullet length discipline when reworking for a new application:** don't expand an existing bullet by more than **10%** of its character count. It's fine to cut it by up to **20%**.
5. **Role/section headers can be renamed per application** based on how they were phrased in previous CV versions. Check the archive for a title that fits the current framing better rather than treating the base resume's header as fixed.
6. **Be precise about what a metric measures: don't let a partner's or integration's scale read as the platform's own reach.** If integrations reached a partner's existing user base, it's fine to say "integrations that reached ~500M WAU", not fine to say "a 500M-WAU platform". When a platform-scale number is genuinely needed, use the platform's own reach.
7. **Surface mentorship whenever a JD asks about people management, mentorship, or team development.** Each mentorship has a specific focus, so don't blur them together. Example phrasing: "Formally mentored a junior PM on discovery methodology: customer interviews, user testing, MVP definition."

   This is genuine people-development experience but **not the same as having direct reports**. When a JD specifically wants direct-report management, name mentorship as the closest real evidence, and don't imply it's equivalent.
8. **Default bullet structure: accomplishment first, then how it was measured, then how it was done:** "Accomplished [X], as measured by [Y], by doing [Z]." Not method-first ("Did Z, which caused Y"). Sourced from Google's own official resume guidance, but it's good general practice, so use it as the default shape for new bullets across all applications.
9. **When a JD lists explicit Minimum Qualifications, treat them as a hard checklist, not just a lens.** The resume needs to *visibly and directly* demonstrate each MQ. Don't rely on generally-relevant experience to imply it. This matters most at companies that screen against MQs explicitly (Google names this outright in its own application guidance), but check it for any JD that lists MQs separately from preferred qualifications.
10. **When trimming a work-history section that's too dense (many roles on one page), set a tiered character budget before cutting. Don't cut randomly.** Tier by recency + relevance to the target role: current/most-relevant roles ≤150 chars/bullet; an older-but-still-strong role (a standout 0-to-1 or metric-heavy role) ≤160 chars/bullet; oldest/least-relevant roles ≤110 chars/bullet and 2–3 bullets max. When a bullet must run over its tier's cap because it's carrying several distinct real facts (multiple named partners, or several partnerships each tied to a different MQ/PQ), flag it as an explicit exception rather than cutting a real fact down to fit: losing genuine detail to hit a character count is a worse trade than one long bullet. Also, when cutting bullets to fit a count cap, check each candidate against the MQ/PQ list first. Don't drop a bullet that's the resume's only coverage of a Minimum Qualification just because it lacks an outcome metric.

26. **Open every role with a remit bullet.** The first bullet of each role states what the user owned: the product/platform, its scope, and who it served. It can also carry the role's headline impact (e.g. "Owned enterprise billing and licensing across self-serve and resold channels, lifting license attach from 18% to 84%"). The remaining bullets are achievements in rule 8's shape, ordered by relevance to the JD. Why: screening recruiters often read only the first bullet per role, so it must answer "what did this person own, at what scale?" before any single win. For a one-bullet role, that bullet is the remit bullet.

27. **Aim for one page.** Use the single-column template. If a draft runs over, apply rule 10's budget and cut the least relevant content before shrinking the type further.

## Education

11. **Short courses/continuing education are real and can be listed, but honestly.** Name the institution and topic, not a formal-sounding unit or program name that implies degree-level enrollment (e.g. avoid "Stanford School of Engineering" for a short/online course). Don't specify exact duration/scope in a way that overstates a short course as something longer. When drafting a CV that uses one of these, confirm the exact course name/platform with the user rather than inventing plausible-sounding wording.

## Cover letter

12. **Avoid "plus" as a connector.** Use "alongside," a semicolon, or restructure the sentence.
13. **Tone: declarative, not narrative, but a claim-first opening sentence is optional per paragraph, not mandatory.** Lead a paragraph with a claim only when the claim itself is a plain, substantive statement of a real category of experience (e.g. "I have deep experience executing strategy across functions, divisions, and external partners"). If the claim would only be a punchy rhetorical contrast ("I do X, not Y") that adds no information beyond what the evidence already shows, cut it and open the paragraph directly with the strongest concrete example instead. Evidence-first is a fine default; claim-first is the exception for when there's a real point to make first. This applies throughout, not just to topic sentences: cut any "X, not Y" rhetorical contrast, hedge, or self-praising aside that doesn't add a new fact (e.g. "not just observe," "that few others can match"). Avoid first-person scaffolding like "I recognise that pattern" and "I don't just study X, I build it." "What draws me to X" is fine specifically in the motivation section, when immediately followed by a concrete, genuine reason: it reads as sincere there rather than as filler. Pyramid-paragraph openings are governed by rule 16's point-echo requirement (mandatory there); this rule's claim-first-is-optional framing applies to the motivation paragraphs and to sentence-level tone generally.
14. **Open and close with simple, fixed templates.** Immediately after "Dear [Company] team,", use one of two opener patterns: (a) "I'm excited to be considered as a [title] for [team name], given my background at [company] [experience/motivation point 1], as well as [experience/motivation point 2], and [experience/motivation point 3]." or (b) "I'm applying for a position as [title] with [company] because my career has centred on [experience/motivation point 1], [experience/motivation point 2], and [experience/motivation point 3]." Each of the three points should map 1:1 to the pyramid paragraph that elaborates it below, in the same order: the opening previews exactly what the body proves, not a looser summary. Close with a brief, simple thank-you, "Many thanks for your consideration,", rather than a "let's talk/discuss" call-to-action sentence: simpler and less salesy.
15. **Structure the letter ~2/3 Minto pyramid, ~1/3 motivation.** The first ~two-thirds makes the case for fit: one paragraph per pillar (per rule 13), each a self-contained claim → evidence unit, MECE against the others (no two pillars arguing the same thing). The final ~third shifts entirely to genuine motivation: why *this* role or company specifically, not more qualification-stacking. The motivation content must come from the user, not be invented. Ask if it isn't already established for this application. (See rule 16 for how each pyramid paragraph should open.)
16. **Each pyramid paragraph opens with a point-echo, then bridges into evidence with a plain factual statement.** Its first sentence restates, paraphrased not verbatim, the specific point it was assigned in the opener's preview (rule 14). This is what makes the pyramid recursive: the opener decomposes the top-line claim into MECE points, and each paragraph is that point's own mini-pyramid, so it needs its own governing sentence before its own evidence. This applies to every pyramid paragraph, including the first. After the point-echo, bridge into evidence plainly ("I also...", "For the same platform...", "At the same company..."), never with a suspense-building setup line ("X wasn't enough, so...", "That also meant...") that manufactures narrative tension before stating the fact. State the fact directly; let the paragraph order and point-echoes carry the logic.
17. **Never fabricate or misattribute a stat.** When using outside research (news, competitor analysis, a shared AI research doc) to inform a letter, filter to only what's verified as belonging to the specific team/product being applied to. Drop anything attributed to a different product line, or that can't be verified.
18. **Default length: 3–4 paragraphs, ~300–400 words**, unless explicitly asked to expand. This default exists so letters don't drift longer by accretion across review rounds.
19. **The moment CV work is done and work moves to the cover letter, research the company/role first:** business model, customers, revenue sources, use cases, product, growth trajectory, what's genuinely impressive, recent wins, strategic bets, etc., before drafting anything. Present findings to the user so they can supply genuine motivation from them (per rule 15). Never invent motivation from the JD alone.

## Always

20. **Maintain an explicit "known gaps, flagged honestly" list per application.** Don't paper over real mismatches. Update it as new information partially closes a gap, and don't delete the history of what was closed.
21. **Review bio, work history, and cover letter in chat before finalizing.** Draft and show each component for review rather than only writing straight to a file. The user approves and edits in the conversation first.
22. **When creating a cover letter as a Google Doc, set the body font to match the resume's typeface,** regular weight.
23. **When a JD names specific qualities with exact adjectives** (e.g. "extremely ambitious," "high self-standards," "generously... without the expectation of receiving in return"), echo the JD's own words directly in the relevant claim sentence, not just a paraphrase. It strengthens the MQ match for both a human scanner and any keyword/ATS screen. Extends rule 9's MQ-checklist discipline to cover letters specifically.
24. **No sentence in a cover letter (or other prose) starts with a verb, including gerunds** (e.g. not "Redesigning the funnel cut…" but "My redesign of the funnel cut…"). Open with a subject (I, my, the team, a noun phrase) or a short prepositional/context phrase. Resume bullets are exempt (they conventionally start with action verbs).
